AI Agent를 개발할 때 어려운 문제 중 하나는 **최종 결과만으로는 내부에서 어떤 일이 일어났는지 파악하기 어렵다**는 것입니다. 따라서 AI Agent를 안정적으로 개발하고 운영하려면 결과뿐 아니라 **그 결과가 만들어지는 과정 전체를 관측할 수 있어야 합니다.**

이러한 문제는 AI Agent가 등장하기 전부터 복잡한 소프트웨어 시스템에서 존재했습니다. 특히 클라우드와 마이크로서비스가 확산되면서 여러 구성 요소에 걸친 실행 흐름을 추적해야 할 필요성이 커졌습니다.

이러한 문제를 해결하기 위한 공통 기반으로 등장한 기술이 **OpenTelemetry(OTel)**입니다.

## 1. OpenTelemetry가 등장한 배경

OpenTelemetry가 등장한 배경에는 크게 두 가지 문제가 있습니다.

- **실행 흐름의 단절:** 여러 서비스에 분산된 기록을 하나의 요청으로 연결하기 어렵습니다.
- **관측 도구의 파편화:** 도구마다 계측 방식이 달라 특정 제품에 종속되기 쉽습니다.

### 1.1. 시스템이 복잡해지면서 전체 실행 흐름을 파악하기 어려워졌습니다

과거에는 하나의 애플리케이션이 단일 서버에서 실행되는 경우가 많았습니다. 하지만 클라우드와 마이크로서비스 아키텍처가 확산되면서 하나의 요청이 여러 서비스와 프로세스를 거쳐 처리되는 구조가 일반화되었습니다.

예를 들어 주문 시스템에서 하나의 요청은 다음과 같이 처리될 수 있습니다.

```
사용자 요청
    → 주문 서비스
    → 재고 서비스
    → 결제 서비스
    → 외부 결제 시스템
```

사용자가 주문 과정에서 지연을 경험했다면, 단순히 각 서버가 정상적으로 작동하는지만 확인해서는 원인을 파악하기 어렵습니다. 각 서비스에 로그가 존재하더라도 **서로 다른 서비스의 기록이 연결되지 않으면 전체 실행 흐름을 파악하기 어렵기 때문입니다.**

이러한 문제는 AI Agent에서도 유사하게 나타납니다.

AI Agent는 하나의 요청을 처리하기 위해 LLM 호출, Tool 실행, 데이터 검색 등 여러 작업을 수행할 수 있습니다.

따라서 어떤 작업이 어떤 순서로 실행되었으며, 각 작업의 결과가 다음 단계에 어떤 영향을 미쳤는지 연결해서 확인할 필요가 있습니다.

### 1.2. 관측 도구마다 데이터를 수집하는 방식이 달랐습니다

또 다른 문제는 관측 데이터를 수집하는 방식이 도구마다 달랐다는 점입니다.

애플리케이션에서 실행 정보를 기록하도록 코드나 라이브러리를 구성하는 작업을 **계측(Instrumentation)**이라고 합니다.

공통 표준이 없다면 사용하는 관측 도구에 맞춰 계측을 구현해야 합니다. 특정 모니터링 제품의 API에 의존하는 경우, 도구를 변경할 때 애플리케이션의 계측 코드까지 수정해야 할 수 있습니다.

OpenTelemetry는 이러한 문제를 해결하기 위해 등장한 오픈소스 관측성 프레임워크입니다.

## 2. OpenTelemetry는 무엇을 해결하는가?

OpenTelemetry의 핵심은 **관측 데이터를 생성하고 수집·전달하는 방식을 표준화하는 것**입니다.

OpenTelemetry가 다루는 대표적인 데이터는 로그(Logs), 메트릭(Metrics), 트레이스(Traces)이며, 이를 통틀어 **텔레메트리(Telemetry) 데이터**라고 부릅니다.


| 데이터     | 역할                       |
| ------- | ------------------------ |
| Logs    | 실행 중 발생한 이벤트를 기록         |
| Metrics | 요청 수, 응답 시간 등의 수치를 측정    |
| Traces  | 하나의 요청이 거친 작업과 실행 흐름을 추적 |


특히 분산 시스템에서는 **Trace**가 중요합니다.

Trace는 하나의 요청에 속한 여러 작업의 실행 흐름을 나타내며, 각각의 작업 단위를 Span이라고 합니다. OpenTelemetry는 Trace ID와 Span ID 등의 정보를 포함하는 컨텍스트를 서비스 간에 전파하여 서로 다른 작업의 관계를 추적할 수 있도록 지원합니다.

이를 위해 OpenTelemetry는 다음과 같은 공통 기반을 제공합니다.

1. **데이터 생성 방식의 표준화**
   - 공통 사양에 기반한 API와 SDK를 제공하여 언어와 프레임워크에 관계없이 일관된 방식으로 계측할 수 있도록 합니다.
2. **데이터 의미의 표준화**
   - Semantic Conventions를 통해 속성의 이름과 의미를 정의하여 데이터를 일관되게 해석할 수 있도록 합니다.
3. **분산된 실행 흐름의 연결**
   - Context Propagation을 통해 서로 다른 서비스와 프로세스에서 발생한 작업을 하나의 요청 흐름으로 연결합니다.
4. **관측 데이터 전달 방식의 표준화**
   - OTLP, Exporter 등을 통해 데이터를 관측 백엔드로 전달하며, 필요에 따라 Collector에서 데이터를 수신·처리·전달할 수 있습니다.

전체적인 데이터 흐름은 다음과 같습니다.

```
애플리케이션
     ↓
OpenTelemetry 계측
     ↓
Logs / Metrics / Traces
     ↓
(선택) OpenTelemetry Collector
     ↓
관측 백엔드
(저장 · 시각화 · 분석)
```

여기서 주의할 점은 **OpenTelemetry 자체는 모니터링 대시보드나 분석 도구가 아니라는 것**입니다.

OpenTelemetry는 관측 데이터를 생성·수집·전달하는 공통 기반을 제공하며, 데이터를 저장하고 시각화하는 역할은 별도의 관측 백엔드가 담당합니다.

## 3. AI Agent 관측성과의 연결

일반적인 소프트웨어 시스템에서는 요청 처리 시간, 오류 발생 여부, 서비스 간 호출 관계 등을 중심으로 상태를 파악합니다.

하지만 AI Agent에서는 이러한 정보만으로 충분하지 않습니다.

예를 들어 Agent가 모든 Tool을 정상적으로 호출하고 오류 없이 응답했더라도, 검색한 정보가 부적절하거나 LLM이 잘못된 결론을 내렸다면 사용자는 잘못된 답변을 받게 됩니다.

즉, **시스템이 정상적으로 실행되었다는 사실과 Agent가 올바른 결과를 생성했다는 사실은 다릅니다.**

따라서 AI Agent의 관측성에서는 실행 흐름뿐 아니라 각 단계에서 어떤 입력을 받고, 어떤 결과를 생성했는지도 확인할 필요가 있습니다.

이때 Tracing을 활용하면 LLM 호출과 Tool 실행을 하나의 요청 흐름으로 연결하여 분석할 수 있습니다. 적절한 계측이 구성되어 있다면 프롬프트, 응답, 토큰 사용량 등의 정보도 함께 기록할 수 있습니다.

다만 OpenTelemetry가 이러한 정보를 자동으로 모두 수집하거나 AI 응답의 품질을 직접 평가하는 것은 아닙니다.

OpenTelemetry가 관측 데이터를 다루는 공통 기반을 제공한다면, **Langfuse는 LLM과 AI Agent의 실행 흐름을 시각화하고 분석하는 데 특화된 도구**입니다.

결국 OpenTelemetry의 가치는 단순히 로그를 더 많이 수집하는 데 있지 않습니다. 서로 다른 시스템과 도구에서 생성되는 관측 데이터를 일관된 방식으로 다룰 수 있게 한다는 점에 있습니다.

다음 글에서는 이러한 개념을 바탕으로 **Tracing의 구조와 Langfuse를 활용한 AI Agent 실행 흐름 분석**을 살펴보겠습니다.
